# 技能名称：重投诉原因(1~9类)深度分析与归因

# 适用智能体：analytics-agent（数据分析专员）/ ticket-agent（工单诊断专员）

# 触发条件：用户询问「为什么重投」「重投原因分析」「原因归类查询」「查一下超时或未解决的重投单」

## 一、技能使用背景与数据前置要求

当用户发起重投诉原因分析请求时，你必须严格按照以下 1~9 类的判定规则，在数据库中进行逻辑匹配与统计；**所有数字必须来自当次 `scheme_db_query`，禁止编造**。

| 项 | 说明 |
|----|------|
| 物理表 | `chongtou_root_cause_detail`（逻辑名 `chongtou`） |
| **重投总量口径** | **仅** `"三节点是否重投" = '是'` 才计入重投量 / 占比分母；禁止用未过滤的 `COUNT(*)` 或探针 `total_rows` |
| **时间基准** | 统计与比较一律用**当前行**的 `"派单时间"`（勿用 `updated_at` /「今年以来」等臆造区间） |
| **数据回溯** | 原因 1~9 中「上一单」字段：组内上一个工单（同号码等） |
| 间隔参数 | `CHONGTO_REPEAT_GAP_DAYS`（环境配置，常见 3 或 7） |

常用字段：`"投诉所属地市"`、`"工单编号"`、`"派单时间"`、`"投诉问题号码"`、`"三节点是否重投"`、`"重投原因"`、`"上一张工单原因"`、`"处理结果"`、`"投诉原因二级分类"`、`"投诉原因三级分类"`、`"预计完成时间"`、`"解决时间"`、`"方案库处理结果"`。

表内 `"重投原因"` 多为已落库标签；做 1~9 类归因时优先按下方规则用窗口函数/`CASE` 重算；若只要看板同口径，可对 `"重投原因"` 做 `GROUP BY`（仍须 `"三节点是否重投"='是'`）。

### 时间过滤（必做）

- **用户未指定时间 → 默认「近一个月」**：先查库表派单时间按月分布，取**有数据的最近一个自然月** `cur_ym`（如 `2026-10`），分析该月；**禁止**用全表累计或「今年以来」。探针全表 `chongtou_yes` **不能**当某月全省总量或占比分母。
- 回答开篇须写明：`统计月份：YYYY-MM（派单时间；用户未指定，默认近一个月）`。
- **环比必查**：无论默认近一月还是用户指定某月，都要查上月 `prev_ym` 同口径单量，输出环比增减与环比%（上月为 0 则写「上月无数据/无法算环比%」）。可与当月同 SQL：

```sql
-- 先取最近有数月份（用户未指定时）
SELECT substring("派单时间" from 1 for 7) AS ym, COUNT(*) AS n
FROM "chongtou_root_cause_detail"
WHERE "三节点是否重投" = '是'
  AND "派单时间" ~ '^[0-9]{4}-[0-9]{2}'
GROUP BY 1
ORDER BY 1 DESC
LIMIT 3;

-- 当月 + 上月同粒度（示例：长沙；换成实际 cur_ym / prev_ym）
SELECT
  COUNT(*) FILTER (WHERE substring("派单时间" from 1 for 7) = '2026-10') AS cur_n,
  COUNT(*) FILTER (WHERE substring("派单时间" from 1 for 7) = '2026-09') AS prev_n,
  COUNT(*) FILTER (
    WHERE substring("派单时间" from 1 for 7) = '2026-10'
      AND btrim("投诉所属地市") LIKE '%长沙%'
  ) AS city_cur,
  COUNT(*) FILTER (
    WHERE substring("派单时间" from 1 for 7) = '2026-09'
      AND btrim("投诉所属地市") LIKE '%长沙%'
  ) AS city_prev
FROM "chongtou_root_cause_detail"
WHERE "三节点是否重投" = '是'
  AND "派单时间" ~ '^[0-9]{4}-[0-9]{2}'
  AND substring("派单时间" from 1 for 7) IN ('2026-09', '2026-10');
```

- **整月**优先：`substring("派单时间" from 1 for 7) = 'YYYY-MM'`（与看板一致）。
- **半开区间**只能 `>= 月初 AND < 次月-01`，**禁止** `< 月末日`。
- **同粒度占比**：地市量与全省量必须同一套 WHERE（含三节点=是 + 同一月份）。

## 二、核心判定规则库（1~9类）

### （一）网络原因类（原因 1~4）

*前提：上一单「投诉原因二级分类」=「网络原因」，且上一单「处理结果」≠「已解决」。*

- **原因 1（处理超时且已解决）**
  - 上一单「方案库处理结果」为 `601011901` 或包含「已解决」；
  - 且上一单的「解决时间」 < 当前重投行的「派单时间」。
- **原因 2（超时未解决）**
  - 上一单有「解决时间」时：解决时间 > 预计完成时间；
  - 上一单无「解决时间」时：当前派单时间 > 上一单预计完成时间。
- **原因 3（短期内重投）**
  - 当前派单时间未超过上一单预计完成时间；
  - 且两次派单时间间隔 **< CHONGTO_REPEAT_GAP_DAYS 天**。
- **原因 4（长期后重投）**
  - 当前派单时间未超过上一单预计完成时间；
  - 且两次派单时间间隔 **≥ CHONGTO_REPEAT_GAP_DAYS 天**。

### （二）非网络原因类（原因 5、6、7）

*前提：上一单「投诉原因二级分类」=「非网络原因」，且组内存在上一单（同号码 + 投诉三级分类 + 派单序号），且上一单「投诉原因三级分类」属于指定清单。*

- **原因 5（常规非网络问题）**  
  上一单三级分类 ∈ `["套餐资费", "宽带问题", "外部网站问题", "工单错误", "业务咨询", "第三方软件通话问题", "CPE问题"]`
- **原因 6（限速问题）**  
  上一单三级分类 = `"用户被限速"`
- **原因 7（其他非网络问题）**  
  上一单三级分类 ∈ `["其他", "终端问题", "SIM卡问题", "用户自动恢复", "重复派单"]`  
  **或**上一单的「处理结果」「二级分类」「三级分类」均为空。

### （三）已解决后的重投类（原因 8、9）

*前提：上一单「处理结果」=「已解决」，且上一单「投诉原因二级分类」=「网络原因」。*

- **原因 8（相同问题重投）**  
  当前与上一单的「投诉原因二级分类」和「三级分类」**均一致**。
- **原因 9（不同问题重投）**  
  当前与上一单的「投诉原因二级分类」**或**「三级分类」**不一致**。

## 三、执行规范与输出要求

1. **读取参数**：查询前确认 `CHONGTO_REPEAT_GAP_DAYS`（未知则先按 3；可在分析正文需要处写明，不必塞进文末数据来源）。
2. **只读 SQL**：`scheme_db_query`；中文列名双引号；1~9 归因时先对全表做 `LAG`，**最终计数 WHERE 必须 `"三节点是否重投"='是'`**（可加月份/地市）。
3. **看板同口径汇总示例**：

```sql
SELECT btrim("重投原因") AS reason, COUNT(*) AS cnt
FROM "chongtou_root_cause_detail"
WHERE "三节点是否重投" = '是'
  AND "派单时间" ~ '^[0-9]{4}-[0-9]{2}'
  AND substring("派单时间" from 1 for 7) = '2026-10'
GROUP BY 1
ORDER BY cnt DESC
```

4. **输出分流（先判断用户意图，再选版式）**

| 场景 | 识别 | 版式 |
|------|------|------|
| **一般问答（默认）** | 问多少、占比、排名、原因分布、简单对比等；**未**说「深度分析 / 出报告 / 详细报告 / 全面剖析」 | **约 200～300 字**：2～4 句结论 + 最多 **1** 张关键表（原因或地市）+ 文末来源表。禁止一～四章长报告、禁止堆多张表/风险等级/改进建议长文 |
| **深度分析 / 报告** | 用户明确说「深度分析」「出报告」「详细报告」「按报告格式」「全面分析」等 | 下方「报告体」完整分节 |

**一般问答示例结构**（约 200～300 字，须含环比）：
- 开篇标明统计月份（默认近一月时注明「用户未指定，默认近一个月」）。
- 结论：重投总量（三节点=是）、地市量与占比/排名（若问地市）、**环比**（较上月单量增减与 %）。
- 相关信息：最多 1 张小表（如 TOP 原因或关键构成）。
- 文末来源表（时间维度填当月 `YYYY-MM`）。

**报告体**（仅深度分析/报告时用；`###` 分节 + 表）：
   - **一、整体情况**：总量、占全省/排名、**环比（必有）**。
   - **二、结构分析**：区县/地市、1~9 或落库原因、可选业务分类。
   - **三、超时/未解决**：有数才写。
   - **四、根因洞察与建议**：须贴数字，勿空泛。
   - **文末数据来源**（两种版式都要，固定最后）：

```markdown
| 数据来源 | 时间维度 |
|----------|----------|
| chongtou_root_cause_detail | 2026-10 |
```

     （不要写过滤/地市/原因明细；默认近一月时时间维度仍写该月 `YYYY-MM`。）

5. **输出前自检**（对不上就重查，禁止改文案圆场）：
   - 重投过滤在场；文案时段=SQL 过滤；分子分母同查询；占比可复算；未用 `<月末日`；空原因占比异常高（如 >50%）视为漏过滤。
   - **默认月 + 环比**：未指定时间则已用最近有数月；结论中已含上月对比数字（来自查询，非编造）。
   - **版式自检**：用户没要报告时，禁止输出「××深度分析报告」及一～四章长文。
